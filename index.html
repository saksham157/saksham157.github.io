How my code reaches Kubernetes

Every project I build follows the same delivery path. A developer only pushes code. The platform does the rest, and a change can only enter the cluster through Git.

  1. git
    GitHubpush triggers a webhook
  2. ci
    Jenkinsshared library runs the stages
  3. qa
    pytest + SonarQubetests and a quality gate
  4. img
    Dockerimage tagged with the build number
  5. git
    GitOps repoJenkins commits the new tag
  6. cd
    ArgoCDsees the commit and syncs
  7. k8s
    KubernetesHelm chart, health probes
  8. aws
    AWSVPC and EKS from Terraform

Jenkins never runs kubectl and holds no cluster credentials. It only writes to Git. If a deploy goes wrong, rolling back means reverting one commit.

One shared pipeline for every service, delivered by GitOps

When every team writes its own Jenkinsfile, the stages drift apart and some teams skip the quality checks. I moved the whole pipeline into a Jenkins Shared Library. A service repo now needs two lines to get build, test, code-quality gate, Docker image and GitOps delivery. ArgoCD then deploys the change to Kubernetes from a separate Git repo.

Working end to end. Build #35 went from push to updated GitOps repo in 36 seconds.

Architecture

How a change moves through it

  1. A push starts the pipelineGitHub sends a webhook to Jenkins. The service's Jenkinsfile loads my library and calls one function.
  2. Tests run in a clean environmentEach build creates its own Python virtual environment and runs 13 pytest tests, so nothing depends on what is installed on the agent.
  3. SonarQube decides if the code may shipThe pipeline waits for the quality gate. If it fails, the build stops before any image is created.
  4. Docker builds and pushes the imageThe image is tagged with the Jenkins build number, for example python-app-code:35, so every deploy maps to one build.
  5. Jenkins commits the new tag to the GitOps repoIt updates values.yaml in gitops-manifests and pushes, as the user jenkins-ci.
  6. ArgoCD syncs the clusterArgoCD sees the commit and rolls out the new version. In the screenshots it shows Healthy and Synced, with nine revisions, all delivered through Git.

What broke, and how I fixed it

Pod stuck in CrashLoopBackOff, hiding two more bugs

Cause. The app was a script. It ran once and exited, and Kubernetes kept restarting it. The logs showed no error at all.

Fix. I rewrote it as a Flask service with a /health route. That exposed a Service sending traffic to port 3000 while the app listened on 5000, and then an image that had no Flask because the Dockerfile ignored requirements.txt. I fixed each one in turn.

Jenkins showed SUCCESS, but no stage ran

Cause. The Jenkinsfile called the library step without parentheses, so Groovy treated it as a property and the pipeline body never ran.

Lesson. A green build is not proof that work happened. I now check that the stages actually ran.

pip install blocked on the build agent

Cause. Python 3.14 blocks system-wide installs (PEP 668).

Fix. A fresh virtual environment for every build.

Helm values never reached Git

Cause. The stage assumed the GitOps repo was already in the workspace, and a sed command broke on nested quotes.

Fix. An explicit clone before editing, and a simpler sed expression.

The same AWS environment, built the same way, every time

Environments built by hand in the console drift apart, and two people running Terraform at the same time can corrupt the state. I wrote reusable Terraform modules for the network, security groups, IAM and EKS. Dev, test and staging are built from the same modules, each with its own CIDR range and its own locked, encrypted state file.

Decisions I can explain

One NAT gateway, on purposeIt is cheaper than one per zone. The cost: if us-east-1a fails, nodes in 1b lose outbound internet. That is fine for dev. Production would get one NAT per zone.
Bootstrap is separateThe state bucket cannot be stored in the state it creates, so it has its own small Terraform root.
One state file per environmentA mistake in dev cannot touch staging.
No AWS keys inside JenkinsAn IRSA role lets the Jenkins service account in Kubernetes assume AWS permissions through OIDC.

Know what a Terraform change costs before you apply it

Teams usually find out what new infrastructure costs when the monthly bill arrives. In this project every pipeline run prices the Terraform plan with Infracost, stores the result in Postgres, and shows the trend in Grafana. The last step is a guardrail that fails the build when a change pushes cost past a budget.

How it works

  1. Jenkins runs terraform planOn the CI server, next to the Terraform and Infracost CLIs.
  2. Infracost prices the planIt returns the monthly cost and a breakdown per resource as JSON.
  3. A Python script stores itOne row per build in Postgres on a second server: build ID, time, service, total and the breakdown.
  4. Grafana shows the trendCost over time, so a jump is visible at the build that caused it.
  5. A guardrail blocks expensive changesPlanned: fail the build or alert when cost rises past a threshold.

What broke, and how I fixed it

Postgres refused remote connections

Cause. The listen address setting was still commented out, so the database only listened on localhost.

Lesson. Check what the running process does, not only the file I edited.

Insert denied, even with table rights

Cause. The auto-increment ID uses a separate sequence, and the writer user had no rights on it.

Fix. A grant on the sequence too.
